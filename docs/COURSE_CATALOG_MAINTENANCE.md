# 408 课程目录维护规则

更新时间：2026-08-28

## 1. 两套内置课程必须分离

- `site/data/oxygen.json`：只保存“历年 408 真题讲解”目录。
- `site/data/oxygen-reinforcement.json`：只保存“27考研408四科强化”内置基线目录。
- 真题自动同步不得覆盖、重写或清空强化课文件。
- 强化课同步不得写入真题文件。

这两个文件承担不同职责，任何“为了复用一个课程文件而整体替换”的修改都视为高风险变更。

## 2. 四科强化的当前完整基线

当前已确认的最低完整课时数：

- DS：37
- CO：29
- OS：29

## 3. 静态基线与 Supabase 的关系

`oxygen-reinforcement.json` 是内置强化课的保底基线；Supabase `course_catalog_items` 是后台可管理的云目录。

规则：

1. 云端可以补充、更新课程元数据，也可以增加自定义课程。
2. 云端数据不得让内置强化课少于静态基线。
3. 前端必须采用“静态基线 + 云端增量合并”，不能用一份不完整云快照整体覆盖基线。
4. 如果 Supabase 内置目录少于静态基线，应先修复云端，再发布；前端基线守卫仍应保留作为第二道保险。
5. 后台的删除/停用操作不得级联删除历史用户进度。

当前前端守卫：`site/assets/js/course-catalog-baseline.js`。

## 4. 用户进度是独立数据，禁止跟目录一起删除

- 用户完成状态和笔记存放在 `course_states`。
- `progress_id` 一旦用于用户进度，不允许因为改标题、改排序、改 URL 而重新生成。
- 删除课程默认只做停用/归档，不物理删除已有进度。
- 恢复课程时应继续使用原来的 `progress_id`。

## 5. 发布前必须检查的课程完整性

每次涉及 `/408/`、课程后台、课程同步、Supabase 迁移或课程 JSON 的修改，至少检查：

1. 真题目录和强化目录是否仍是两个独立文件。
2. 强化课数量是否不低于 DS 37 / CO 29 / OS 29 / CN 28。
3. CN 是否仍包含“应用层选择题专题”。
4. Supabase `oxygen-reinforcement` 四科数量是否与静态基线一致或更多。
5. `course_states` 总量及已有笔记数量是否在目录维护过程中保持不变。
6. `/408/` 中 DS / CO / OS / CN 均能切换，课程数量正确。
7. 勾选课程、写备注不会触发 `location.reload()` 或整页跳转。
8. GitHub Pages 最新 workflow 必须成功后才能认为修复完成。

## 6. 这次 CN 回退的根因

2026-08-28 排查发现：

- 静态 `oxygen-reinforcement.json` 中 CN 实际有 28 节，是完整的。
- Supabase `oxygen-reinforcement` 中当时只有 CN 前 14 节。
- `/408/` 使用云目录优先，因此不完整的 14 节云快照覆盖了完整静态目录，页面看起来像“CN 回退”。

修复方式：

- 补回 Supabase 缺失的 CN 第 15—28 节；
- 保持原有 `progress_id`，不改用户进度；
- 增加静态基线合并守卫，防止不完整云目录再次把内置课缩短；
- Pages 发布校验增加四科最低完整数量和 CN 末尾课时检查。

## 7. 后续自动同步约束

当前“408 Course Sync”只负责历年真题讲解集合时：

- 只更新真题目录；
- 不修改强化课基线；
- 不删除 `course_states`；
- 没有真实集合变化就不提交；
- 需要扩展到强化课程自动同步时，必须先单独实现“增量合并、永不缩短基线”的同步器，不能复用真题的替换逻辑。

## 一句话维护原则

**课程目录可以新增和修正，但内置课程不能因为云同步、迁移或重构而变少；目录和用户进度永远分离。**
